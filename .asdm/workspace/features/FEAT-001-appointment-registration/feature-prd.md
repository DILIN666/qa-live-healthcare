# Feature PRD: 预约挂号

**Feature ID**: FEAT-001
**Created Date**: 2026-04-29
**Status**: PLANNED
**Language**: 简体中文

---

## 1. 概述

### 1.1 功能简介

让患者可以在线预约医生的线下门诊时段，患者选择医生后可查看该医生的排班并选择可用的门诊时间进行预约，预约成功后收到预约确认信息，医生可在诊室查看自己的预约列表。

### 1.2 目标

- **目标 1**：患者能够浏览医生的门诊排班信息，并选择可用的时段进行预约
- **目标 2**：患者能够查看自己的预约记录，了解预约状态
- **目标 3**：医生能够在诊室查看自己的预约列表，管理预约状态
- **目标 4**：系统支持取消预约和预约提醒功能

---

## 2. 用户故事

### 故事 1：患者预约门诊

**作为** 一名患者
**我希望** 选择医生和门诊时间进行预约
**以便** 能够提前安排线下就诊，避免现场排队等候

**验收标准**：
- 患者可以从医生列表页面进入预约挂号流程
- 患者能够查看医生未来 7 天的门诊排班
- 每个时段显示剩余可预约名额
- 不可预约的时段（如已满、已过）显示为不可选状态
- 预约时需要患者填写姓名、联系方式和就诊备注
- 预约成功后显示预约确认信息，包含预约编号、时间、医生信息

### 故事 2：患者管理预约

**作为** 一名患者
**我希望** 查看和管理我的预约记录
**以便** 了解预约状态，必要时取消预约

**验收标准**：
- 患者可以在个人中心查看所有预约记录
- 预约记录按时间倒序排列
- 显示每条预约的状态（待就诊、已完成、已取消）
- 在预约时间前可取消预约
- 取消预约后释放该时段的可预约名额
- 已完成的预约不可取消

### 故事 3：医生查看预约

**作为** 一名医生
**我希望** 在诊室查看我的预约列表
**以便** 了解当日/近期的就诊安排

**验收标准**：
- 医生登录后可在诊室查看预约列表
- 可按日期筛选查看特定日期的预约
- 显示每位预约患者的基本信息和预约时段
- 可标记患者已到诊
- 可标记患者为"未到诊"

## 3. 功能需求

### 需求 1：医生排班管理

- **ID**: REQ-001
- **描述**: 为每个医生配置门诊排班信息，包括每周的出诊日期和每个时段的可预约名额
- **优先级**: 高
- **关联故事**: 故事 1、故事 3

### 需求 2：预约挂号

- **ID**: REQ-002
- **描述**: 患者选择医生后，查看其排班并选择可用的门诊时段完成预约挂号
- **优先级**: 高
- **关联故事**: 故事 1

### 需求 3：预约记录查询

- **ID**: REQ-003
- **描述**: 患者可以查看自己的所有预约记录，医生可以查看自己的预约列表
- **优先级**: 高
- **关联故事**: 故事 2、故事 3

### 需求 4：取消预约

- **ID**: REQ-004
- **描述**: 患者可以在预约时间前取消预约，系统自动释放该时段的名额
- **优先级**: 中
- **关联故事**: 故事 2

### 需求 5：预约状态管理

- **ID**: REQ-005
- **描述**: 医生可标记患者到诊/未到诊，系统自动更新预约状态
- **优先级**: 中
- **关联故事**: 故事 3

## 4. 非功能需求

### 4.1 性能

- 页面加载时间不超过 2 秒
- 预约操作响应时间不超过 1 秒
- 支持至少 100 个并发用户同时预约

### 4.2 安全

- 预约需要患者身份验证
- 同一时段同一患者不可重复预约
- 取消预约需要验证预约人身份
- 防止恶意刷预约（限制同一 IP 的请求频率）

### 4.3 可用性

- 系统可用性目标：99.5%
- 预约功能故障时不应影响已预约用户
- 提供友好的错误提示和引导

### 4.4 可维护性

- 排班配置支持灵活调整
- 预约数据可导出和统计

## 5. 技术需求

### 5.1 架构考虑

- **数据存储**：使用本地 Store 模拟数据持久化，后续可迁移至后端数据库
- **状态管理**：扩展现有 `store/index.ts`，添加预约相关状态和方法
- **路由设计**：新增 `/appointments`（患者预约记录）和 `/doctor/appointments/:username`（医生预约列表）路由
- **数据模型**：新增 `Schedule`（排班）和 `Appointment`（预约）实体，参考 `data-models.md` 中的扩展模型建议

### 5.2 依赖

- **内部依赖**：
  - `.asdm/contexts/data-models.md` - 数据模型定义
  - `.asdm/contexts/api.md` - API 接口定义
  - `.asdm/contexts/standard-coding-style.md` - 编码规范
  - `.asdm/contexts/standard-project-structure.md` - 项目结构规范
- **外部依赖**：
  - Day.js（日期处理，已在项目中使用）

### 5.3 约束

- 当前为前端单页应用，无真实后端，需使用 Store 模拟数据
- 预约数据存储在浏览器中，刷新后需重新加载
- 排班信息暂时使用 JSON 配置文件管理

## 9. 实施笔记

### 9.1 数据模型设计要点

参考 `data-models.md` 中已有的扩展模型建议：

- `Schedule`（排班）需包含：医生 ID、日期、时段（上午/下午/晚上）、可预约名额、已预约人数
- `Appointment`（预约）需包含：患者信息、医生信息、排班时段、预约状态、创建时间、取消时间

### 9.2 Store 设计要点

扩展 `src/store/index.ts`：

- 新增 `schedules` 状态（排班列表）
- 新增 `appointments` 状态（预约列表）
- 新增 `addSchedule`、`getAvailableSlots`、`createAppointment`、`cancelAppointment` 等方法
- 确保预约名额在创建/取消时正确更新

### 9.3 组件设计要点

- 复用项目现有的 Ant Design Vue 组件风格
- 使用 `Day.js` 处理日期格式化
- 预约表单使用 Form 组件实现验证

### 9.4 页面入口

- 患者端：在 `AppHeader.vue` 或 `Home.vue` 添加「我的预约」入口
- 医生端：在 `DoctorRoom.vue` 添加「预约管理」标签页

## 10. 风险与应对

### 风险 1：预约名额并发问题

- **描述**：多个用户同时预约同一时段，可能导致名额超卖
- **影响**：高
- **应对**：前端层面通过乐观锁机制处理；后续接入后端后由数据库事务保证

### 风险 2：数据持久化问题

- **描述**：当前使用 Store 模拟数据，刷新后数据丢失
- **影响**：中
- **应对**：使用 `localStorage` 持久化预约数据，后续接入后端后由数据库存储

### 风险 3：排班配置复杂度

- **描述**：排班规则可能比较复杂，如有特殊节假日调整等
- **影响**：低
- **应对**：初期简化排班模型，仅支持固定排班；后续扩展
